`ClientConfig.isSameOriginMultiWorkspaceEnabled` initializes a false-by-default atom; native multidomain wins when both flags are set. In opt-in mode credentials use native `signIn`, not the origin-default credentials endpoint. Email verification also uses the native agnostic picker in opt-in mode on the canonical host. Legacy mode retains its existing GraphQL documents and flow.

`useAuth()` exports `selectWorkspaceOnSameOrigin(workspaceId: string): Promise<void>` and `createWorkspaceOnSameOrigin(displayName: string): Promise<void>`. They capture source A before dispatch, call the native mutations with both `input.expectedWorkspaceId=A` and immutable operation context A, validate the returned native LOGIN/target pair, then redeem through native authentication. They do not optimistically set B, store a new JWT or grant permissions. Settings UI owns loading/error/permission presentation. Native role, quota, session and membership failures propagate to that UI.

These menu helpers require a verified current workspace A. The agnostic sign-in picker instead redeems the native LOGIN supplied in `availableWorkspaces` through `getAuthTokensFromLoginToken(token, workspaceId)`. Sign-in preserves the native email-verification step for unverified accounts, and discards that transition if the response belongs to an older session.

Native LOGIN, OTP and recovery completion derive only the target UUID/type LOGIN as client request intent using browser base64 decoding and existing guards. This does not authenticate any claim; the backend verifies signature, purpose, live membership/provider, session binding and JTI. The existing framework LOGIN state carries MFA, including recovery provisioning that does not rotate or reload prematurely.

SSO uses an opt-in standalone typed document requesting optional `workspaceLoginToken`. A scoped exchange is passed to `useAuth().getAuthTokensFromLoginToken` before navigation; the native MFA path stays available. A global exchange remains agnostic. Legacy mode requests its existing document so an old server is not queried for an unknown field.

`loadCurrentUser({ expectedWorkspaceId?: string, commitState?: boolean })` uses no-cache in opt-in mode. It disables Apollo query deduplication per bootstrap operation and verifies response generation and expected B before touching cache or Jotai state. An actual ApolloClient/MockLink delayed-A/current-B test proves two network requests and no A cache/state overwrite. `commitState:false` verifies without committing B. Completion clears cache, awaits confirmed native metadata purge, clears old auth context and performs a full reload to native `/`, closing old forms and constructing fresh clients. Cold bootstrap over a different persisted user/workspace also purges/reloads before committing its response. A cold context with no persisted workspace also requires a confirmed cache/metadata purge before B is committed, without a reload loop. Purge failure is an error, not a reported successful switch.

Apollo contract owned by Claude: operation context string B overrides its captured instance A for the post-redemption bootstrap; explicit `expectedWorkspaceId:null` must omit the header for a cold current-user read whose verified cookie target is not known yet, while `undefined` uses the captured instance. The header never selects a server tenant. Generic user writes must carry the client/form's captured context. Provider/subtree recreation must close forms on scope changes, including storage events from another tab. Late results must be discarded before cache writes. These shared Apollo changes and browser validation remain integration dependencies, not claims made by these hook unit tests.

GraphQL supersession retains native `extensions.code=UNAUTHENTICATED` and `extensions.subCode=SESSION_SUPERSEDED`. It is never retried as a mutation, and a late LOGIN refusal does not redirect the current B session to the login page. Generation checks reject delayed native auth responses before rotating or clearing a later session. An old handler’s finally block cannot release a newer session’s navigation lock.

Language initialization prefers explicit URL, then stored preference, then canonical `fr-FR`. Browser language no longer chooses the application language. Existing explicit profile/preferences remain honored. New signup uses the active language with `fr-FR` fallback; date/timezone detection is unchanged.
