# Session backend de preview P0 — Codex

Branche isolée `chore/p0-preview-backend`, base exacte `bad53ac26b0c3a17a91c91b95be41986c7343836`. Propriété limitée à `scripts/preview-backend-session-p0.mjs` et ce rapport. Aucun original, workflow ou source applicative modifié.

Le helper supervise uniquement les services jetables du runner GitHub Actions : PostgreSQL `127.0.0.1:5432/p0_ci`, Redis `127.0.0.1:6379/0`. Il refuse les overrides de connexion et toute présence de `.env` aux racines du dépôt, du workspace CRM ou du serveur, sans lire ces fichiers. Il génère lui-même `APP_SECRET`, le masque dans les logs GitHub et expurge les secrets des diagnostics enfants. Configuration en production avec hôte loopback, e-mail logger, télémétrie/billing/FDW désactivés et configuration DB désactivée pour conserver les paramètres explicites de session.

Interface de contrôle : `P0_PREVIEW_CONTROL_FILE` est un chemin absolu. Son unique contenu est un objet JSON `{ "serverUrl": "https://backend.example", "frontendUrl": "https://frontend.example" }`. Les deux valeurs doivent être la même origine HTTPS `*.vercel.app`, sans port non standard, identifiants, chemin, query ou fragment. Le helper ne fournit ni tunnel, ni authentification d'accès, ni transport de ce fichier ; l'orchestrateur les apporte séparément et doit remplacer le JSON atomiquement. Aucune URL fournie n'est appelée par le superviseur : les vérifications ciblent les endpoints loopback réels.

Il attend le fichier initial au maximum 15 minutes, puis exécute une seule fois les commandes existantes `dist/database/scripts/setup-db.js` et `dist/command/command.js run-instance-commands --force --include-slow` (cinq minutes maximum chacune). Il n'exécute aucune commande de seed de données métier. Il démarre `dist/main.js` et vérifie `healthz` ainsi que le contrat réel de `client-config`. L’échéance absolue commune gate/backend est fournie par `P0_PREVIEW_EXPIRES_AT`, une date ISO UTC future terminée par Z et au plus 90 minutes après le lancement. Sans cette option, le défaut est 60 minutes depuis le lancement, configurable par `P0_PREVIEW_MAX_MINUTES` (>0, <=90). Ni la readiness ni les actualisations de contrôle ne prolongent cette échéance ; la disponibilité restante après démarrage est donc plus courte que la durée totale. La durée dépend également de la présence du runner CI ; aucun hébergement permanent n'est fourni.

`P0_PREVIEW_START_WORKER=true` lance explicitement `dist/queue-worker/queue-worker.js` avec le même environnement ; son défaut est désactivé. Une modification valide des URLs redémarre Nest et le worker éventuel, puis revérifie les endpoints, sans réinitialiser la DB ni renouveler le secret. Une mise à jour invalide est ignorée avec diagnostic ; le fichier initial invalide fait échouer avant toute initialisation. Une sortie inattendue du serveur ou du worker fait échouer la session. SIGINT/SIGTERM ou expiration arrêtent les groupes de processus enfants dans `finally`, avec SIGKILL après cinq secondes si nécessaire. La readiness constate le processus worker vivant, sans revendiquer une exécution de job métier.

Contrôles exécutés le 29 octobre 2026 : `node --check`, `git diff --check` et 13 refus vérifiés par sous-processus sans lancer de service : invocation locale, PostgreSQL distant, mauvais nom de DB, override PostgreSQL, Redis distant, mauvaise DB Redis, durée >90 minutes, contrôle relatif, option worker invalide, URL HTTP, URL avec identifiants, champ JSON supplémentaire, présence d'un `.env` sentinelle dans une fixture temporaire. Ce dernier contrôle vérifie également que son contenu n'est pas affiché. Les fixtures sont supprimées après vérification.

Limites : pas encore de lancement du superviseur dans GitHub Actions, de test de ses migrations/readiness/restarts/cleanup en conditions réelles, de tunnel, de preview ni de vérification navigateur. Ces preuves doivent provenir du workflow d'intégration après revue et incorporation. Aucune DB ni service local démarré.

Revue croisée : correction du TTL pour partager une échéance absolue avec le gate démarré en premier ; restriction du contrôle à la même origine Vercel que le gate ; arrêt du groupe même si son processus parent est déjà sorti, puis SIGKILL avant retrait du registre de nettoyage. Contrôles ciblés supplémentaires : échéances passée/invalide/>90 minutes refusées, domaines arbitraires/ports/origines différentes refusés, et vraie fixture de processus détaché dont le descendant reçoit SIGTERM après sortie du parent. Aucun service CRM ou DB utilisé.
