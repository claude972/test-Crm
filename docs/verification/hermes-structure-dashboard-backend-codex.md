Une structure réutilise WorkspaceEntity et son unique workspaceId ; UserWorkspaceEntity détermine les adhésions. Aucun schéma, migration ou élévation liée au statut admin serveur. Les queries `/metadata` sont `hermesAuthorizedStructures` et `hermesStructureDashboard`. Liste directe en DB limitée au compte de session actif/non désactivé, adhésions non supprimées, workspaces non supprimés et provisionnés CREATED/ACTIVE. HIDDEN absent de la liste et de la consolidation implicite ; une demande individuelle du HIDDEN déjà actif est seule admise.

Chaque scope demandé est vérifié entièrement avant toute lecture métier. Les contextes utilisateur sont reconstruits par UserWorkspaceAuthContextService ; utilisateur, adhésion et workspace résolus doivent tous correspondre. Le moteur ORM évalue les compteurs company/person/opportunity/task avec `getRepositoryWithContextPermissions`, sans system ni bypass. Sélection limitée à l’ID pour le count, bornes createdAt paramétrées UTC inclusif/exclusif, données supprimées exclues par le moteur existant. Permissions objet/champs et prédicats de lignes restent ceux du repository. Les états interdits/indisponibles sont null et explicites ; les totaux partiels indiquent nombre de contributeurs et nombre de structures. Aucun montant, conversion de devise ou déduplication transverse inventé.

Les cibles réclamant une authentification non satisfaite par la session courante (2FA, SSO ou fournisseur désactivé) restent listables selon l’adhésion mais leurs métriques sont FORBIDDEN sans lecture métier. Le guard refuse API keys, OAuth/application/agents, impersonation et playground. Un espace courant suspendu peut utiliser ce point de lecture pour retrouver ses autres adhésions ; l’espace suspendu lui-même reste exclu en DB. Les adhésions sont relues avant restitution : une suppression/changement de visibilité/renforcement d’authentification pendant le calcul annule la réponse avec une erreur générique.
