La suite utilise le harness natif qui crée `global.app`, `testDataSource` et le serveur HTTP. A/B sont les workspaces Apple/YCombinator provisionnés du seed communautaire ; C est un nouveau workspace synthétique UUID, initialisé par ApplicationService, UserWorkspaceService et WorkspaceService.activateWorkspace. Elle crée quatre utilisateurs jetables example.com : U1=A, U2=A+B, U3=C, U0=sans adhésion ; aucun n’est administrateur technique du serveur. Les adhésions et rôles sont créés par les services natifs. U2 reçoit en B un rôle lecture dont la permission person est explicitement refusée via ObjectPermissionService. Les jetons sont émis en mémoire par AccessTokenService/WorkspaceAgnosticTokenService pour ces adhésions réelles, sans JWT forgé ni lecture/export du secret de signature. Cela teste des credentials de fixture natifs, pas un nouveau mécanisme de switch de session par origine.

Les lignes de recette company/person/opportunity/task sont préparées via WorkspaceOrmManager dans un contexte système explicitement réservé aux fixtures, sans événements métiers. Les appels HTTP `/metadata` du dashboard utilisent ensuite uniquement les jetons utilisateurs, sans bypass. Une période future synthétique fixe [2050-01-01, 2050-02-01) exclut les seeds courants et les jobs asynchrones ; les volumes A/B/C sont distincts. Les personnes portent la même adresse example.com dans chaque structure, sans fusion attendue. Une ligne juste avant début, une ligne exactement à fin et une ligne soft-deleted vérifient les exclusions.

Sept scénarios sont définis : liste A/A+B sans C ; compteurs réels A avec bornes/suppression ; consolidation A+B avec FORBIDDEN person en B et total partiel ; C réellement provisionné avec données lisibles uniquement par U3 ; filtres B/C/inconnu forgés refusés de manière générique ; U0 vide sans scope global ; révocation native soft-delete de l’adhésion B de U2 immédiatement visible au prochain appel et filtre B alors refusé.
