# Workflow de session preview P0 — Codex

Branche `chore/p0-preview-backend`, après `d6477ad8cf81b0e40485a16327fb2005078375fe`. Livraison autorisée limitée au nouveau workflow, à son helper d’orchestration, à l’environnement public du superviseur existant et à ce rapport. Le worktree terminé a d’abord été vérifié propre puis converti en sparse checkout `scripts docs .github` ; ses commits sont conservés. Aucun autre worktree modifié.

`.github/workflows/p0-preview-session.yml` se déclenche sur push `preview/p0-session-*` ou manuellement. Il ne possède que `contents: read`. PostgreSQL 16 / Redis 7 sont créés par GitHub sur loopback ; mot de passe PostgreSQL issu du nouveau secret `P0_PREVIEW_DATABASE_PASSWORD`. Les étapes d’installation immuable, builds shared/client SDK/e-mails, tests SDK, typecheck serveur et compilation Nest reprennent les commandes exactes du workflow backend existant. Aucun browser smoke, seed métier, service local ou infrastructure historique.

Après construction, le workflow télécharge `cloudflared` Linux amd64 version `2026.10.6` et exige SHA-256 `1d356dac769d0dbf62ebe588c4034824bbff98d5790c2f844cc99e0e2f57462d` avant exécution. L’orchestrateur `preview-ci-session-p0.mjs` fixe une seule échéance ISO UTC à maintenant +60 minutes, partagée avec le gate et le superviseur. Il démarre gate loopback et Quick Tunnel, vérifie le refus 403 du tunnel sans secret, puis crée un unique artefact public `tunnel.json` : tunnelUrl, expiresAt, SHA et runId. Aucun log, secret, registre de PID ou contrôle privé n’est joint à l’artefact, conservé un jour. Le gate reçoit seul le secret d’origine ; ni cloudflared ni le backend ne le reçoivent.

La publication de l’artefact précède le lancement du superviseur en attente du contrôle. Le runner relève d’abord le SHA blob du contrôle déjà présent sur `missions/p0-stabilization`, chemin `docs/verification/p0-preview-control.json`, via l’API GitHub authentifiée avec le token à lecture seule. Un contrôle n’est accepté que si son blob diffère de ce baseline ; un contrôle antérieur ne lance donc pas une session. Le polling vérifie taille, type, encodage, origine HTTPS identique `*.vercel.app` sans port non standard/identifiants/query/fragment, et seuls les deux champs publics serverUrl/frontendUrl. L’écriture locale utilise un fichier temporaire puis rename atomique. Le superviseur réinitialise uniquement la DB jetable au premier lancement et redémarre sans réinitialisation si les URLs changent.

Le backend n’hérite ni du token GitHub ni des variables de secret d’origine ; le mot de passe de DB ne lui parvient que dans son URL PostgreSQL encodée et masquée. Le superviseur fixe TRUST_PROXY=loopback, cookies SameSite=lax et origine de cookie autorisée à l’URL de contrôle validée. Worker activé pour push et par défaut pour dispatch ; le dispatch permet de le désactiver explicitement. Le fichier public de contrôle ne contient jamais les secrets. Root gère Vercel, ses secrets/protections et la publication du contrôle après déploiement effectif.

`finally` et une étape GitHub `always()` arrêtent les groupes des processus et retirent les contrôles locaux. Le gate et le superviseur ont aussi leur propre échéance non renouvelable. Le job est borné à 90 minutes, incluant la construction ; la disponibilité restant après Vercel/initialisation est inférieure aux 60 minutes fixées avant tunnel. Les services jetables appartiennent au runner GitHub. Aucune suppression de déploiement Vercel n’est effectuée ici : le propriétaire du déploiement doit gérer cette fin de session et ne pas annoncer une durée supérieure à expiresAt.

Contrôles exécutés : syntaxe Node des deux helpers ; parsing YAML ; assertions structurelles permissions/ordonnancement artefact avant attente/cleanup toujours/portée des secrets ; comparaison exacte des six blocs de build/test avec le workflow backend existant ; fixtures sans service pour garde locale, requête API authentifiée vers la branche imposée, contrôle valide et quatre contrôles invalides, 404 et 403 transport. `git diff --check` et Gitleaks staged sont requis avant commit. Aucun cloudflared, service CRM, DB, déploiement ni workflow distant lancé pour cette livraison.

Limites : actionlint n’est pas installé ; les assertions YAML ne remplacent pas la validation de GitHub Actions. Le workflow dépend des helpers gate/prepare livrés séparément dans la branche d’intégration root ; ils ne sont pas copiés ni modifiés dans cette branche. Commit local pour revue, sans push avant accord root. Le succès de construction, les preuves runtime, Vercel et navigateur restent à produire par la session réelle.
