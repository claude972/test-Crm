# Recette onboarding en ligne — helper préparé

Livraison isolée sur `chore/p0-preview-backend` : uniquement `scripts/check-preview-onboarding-p0.mjs` et ce rapport. Aucun orchestrateur, workflow, source applicative, original ni `.env` lu/modifié. Aucun appel cloud effectué pendant sa préparation.

Invocation autorisée après remise par root du déploiement et du run explicites : `node scripts/check-preview-onboarding-p0.mjs --url https://<deployment>.vercel.app --run-id <runid> --run-metadata /absolute/public-metadata.json --credentials /absolute/private/new-credentials.json --result /absolute/new-redacted-result.json`. Le JSON root doit contenir deploymentUrl (origine exacte sans slash final), runId, expiresAt, sha (40 hex) et environment="preview". La session doit avoir au moins cinq minutes restantes et une échéance à moins de 90 minutes. Aucune URL extérieure à HTTPS *.vercel.app, différence de run/déploiement ou environnement de production acceptée.

Le helper utilise uniquement la CLI Vercel déjà authentifiée : `vercel curl /metadata --deployment <URL> --non-interactive -- --config -`. Il ne lit aucun fichier de token Vercel, ne passe aucun mot de passe ou token applicatif en argv et n’utilise pas d’option debug/trace. Headers Authorization et Origin, documents GraphQL et variables passent dans la configuration curl par stdin. Les sorties brutes de la CLI et les réponses GraphQL ne sont jamais affichées ou enregistrées. La CLI gère elle-même l’accès Deployment Protection autorisé.

Avant mutation, vérification réelle de client-config : password activé, vérification e-mail désactivée, mono-workspace, billing désactivé et serverUrl correspondant au déploiement. Compte exclusivement synthétique `preview-<runid>@example.com`. Son mot de passe aléatoire de 32 caractères est écrit dans un nouveau fichier 0600 hors de tout Git worktree, ouvert de manière exclusive sans suivre de symlink ; aucun token JWT n’y est conservé. Un fichier existant empêche toute réutilisation implicite du compte. Le compte/workspace et ses identifiants privés sont conservés pour la recette utilisateur ; ils disparaîtront avec les services jetables.

Étapes : signUp, signUpInNewWorkspace avec nom non vide, getAuthTokensFromLoginToken avec origine canonique, activateWorkspace et statut CREATED/ACTIVE, skipSyncEmailOnboardingStep, recherche du membre par son e-mail synthétique, updateWorkspaceMemberSettings avec prénom Preview/nom P0 puis relecture réelle, sendInvitations(emails:[]) sans destinataire, et currentUser.onboardingStatus=COMPLETED. Aucun e-mail d’invitation ou de vérification n’est demandé. Le domaine example.com est présent dans emailProvidersSet et évite l’inférence de logo de domaine professionnel. L’activation applique le préremplissage normal du produit, sans commande de seed supplémentaire.

Le CRUD utilise /graphql et un UUID généré exclusivement pour une société nommée P0 synthetic <runid> <suffixe>. Création, lecture, mise à jour, relecture puis suppression et absence vérifiée. Il s’agit de la suppression standard du produit (soft delete), sans destruction physique forcée. En cas d’erreur après tentative de création, finally recherche seulement cet UUID, contrôle son nom exact et tente sa suppression ; tout cleanup non vérifié fait échouer le rapport. Aucun autre enregistrement n’est modifié ou supprimé.

Sources des opérations : mutations frontend auth signUp/signUpInNewWorkspace/getAccessTokensFromLoginToken ; utilitaires serveur de tests GraphQL sign-up/sign-up-in-new-workspace/activate-workspace ; test update-workspace-member-settings-onboarding ; hook onboarding useInviteTeam (Skip envoie emails:[]) ; factories create-one/find-one/update-one/delete-one-operation-factory. Les documents minimaux correspondants sont embarqués afin de fonctionner aussi depuis un checkout sparse, sans lancer le harness de tests qui dépend de comptes seedés.

Preuves locales : syntaxe Node et diff vérifiés ; deux fixtures complètes avec un faux exécutable Vercel (aucun réseau) : parcours réussi avec profil/COMPLETED/CRUD, puis échec GraphQL après création de société avec nettoyage réel de l’état de fixture. Assertions de permissions 0600, absence de mots de passe/e-mail/tokens dans stdout/stderr/rapport, absence de secrets dans argv. Six gardes négatives refusées avant création de fichiers/réseau : environnement non preview, mauvais run, expiration passée, mauvais déploiement, identifiants dans Git, URL non Vercel. Gitleaks staged requis avant commit.

Limites : aucune inscription ou validation API en ligne revendiquée. Les fixtures vérifient le contrôle du helper et le transport stdin, pas les schémas exécutés du déploiement. Pas de test navigateur, cookies, reconnexion interactive, temps réel ou file d’attente métier. Le résultat public ne contient que métadonnées publiques, noms des étapes, statuts et codes d’erreur limités ; jamais les corps de réponse ni les identifiants. Root doit fournir le déploiement réel et lancer explicitement la recette après revue.
